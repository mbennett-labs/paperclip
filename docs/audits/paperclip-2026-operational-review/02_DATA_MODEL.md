# DESIGN EXPLANER: Entity Reference Model

This document maps the Paperclip data model for the AI Agent Company Control Plane. For each entity, it defines: storage schema, keys, relationships, lifecycle, company-scoping, permissions, and notable architectural contradictions.

## Overview
Paperclip is a company-scoped, multi-agent control plane. Every data row is owned by a `company_id`. The core operational cycle is: `issue` → `task` → `run` → `run transcript` → `comment`. Agents interact via `agent_api_keys`. Humans interact via `board_access` tokens. Budget hard-stops and approval gates govern agent autonomy.

## Entity: Company
**Purpose:** The root scoping unit. Every other entity belongs to exactly one company.

**Storage & Keys:**
- **Table:** `companies` (`packages/db/src/schema/companies.ts`)
- **Primary Key:** `id` (UUID, generated by default `gen_random_uuid()`)
- **Fields:** `name`, `slug` (unique), `description`, `settings` (JSONB), `system_projects` (JSONB), `agent_workflow_mode`, `agent_workflow_status`, `created_at`, `updated_at`
- **Unique:** `slug` is globally unique: `UNIQUE("companies_slug_unique").on(table.slug)`

**Relationships:**
- One-to-Many: `users` (`users.company_id`)
- One-to-Many: `projects`
- One-to-Many: `issues`
- One-to-Many: `tasks`
- One-to-Many: `agent_api_keys`
- One-to-Many: `board_access_tokens`
- One-to-Many: `budget_snapshots`
- One-to-Many: `documents`
- One-to-Many: `works`
- One-to-Many: `occupied_parameters`
- One-to-Many: `settings_entries`
- One-to-Many: `agent_workflow_snapshots`
- One-to-Many: `diagnostics`
- One-to-Many: `admins`
- One-to-Many: `audit_logs`
- One-to-Many: `routine_runs`
- Many-to-Many: `teams` via `company_teams`

**Creation Path:**
- `POST /api/companies` → `companyService.create()` (explicit method not read) / `companyService.attachAdmin()` for connecting a user.

**Update Path:**
- `PATCH /api/companies/:id` → `companyService.update()`

**Deletion / Terminal Behavior:**
- Deletion cascades to child entities (e.g., projects, issues). Not explicitly tested in files read but implied by relational structure.

**Company Scoping:**
- All queries to `companies` table are direct (it's the root), but all service methods enforce that sub-entities (e.g., `projectService.list(companyId)`) are scoped to `company_id`.

**Events / PubSub:**
- No direct company events observed; events mostly occur on `tasks`, `runs`, `issues`, and `routines`.

**Tests:**
- Utility `createCompany()` in tests.

**Confidence:** High.

## Entity: User
**Purpose:** Human operator account. Authenticated identity used for board access and admin rights.

**Storage & Keys:**
- **Table:** `users` (`packages/db/src/schema/users.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `name`, `role` (text), `auth_provider` (text), `auth_provider_id` (text), `last_login_at`, `created_at`, `updated_at`
- **Foreign Key:** `company_id` → `companies.id`
- **Unique:** `users_auth_provider_id_unique` on `(auth_provider, auth_provider_id)`

**Relationships:**
- Many-to-One: `companies` (via `company_id`)
- One-to-Many: `admin_logs` (implied by `admins.company_id` not `user_id`, but `users` table owns identity)

**Creation Path:**
- Via `companyService.attachAdmin()` when linking an existing user to a company, or via `companyService.createAdminOnly()` (reads as creating a company with an admin user).

**Update Path:**
- Not observed in routes read; likely board-level.

**Company Scoping:**
- All user queries joined to company or checked via `companyId`.

**Permissions:**
- `role` field controls access. `admins` table explicitly links `user_id` and `company_id` for admin privileges.

**Events:**
- None observed.

**Confidence:** High.

## Entity: Admin (Company Membership)
**Purpose:** Join table linking `users` to `companies` with admin privileges and optional `role` text.

**Storage & Keys:**
- **Table:** `admins` (`packages/db/src/schema/admins.ts`)

- **Fields:** `role` (text, nullable), `created_at`
- **FK:** `user_id` → `users.id`, `company_id` → `companies.id`

**Relationships:**
- Many-to-One: `users`
- Many-to-One: `companies`

**Creation Path:**
- `companyService.attachAdmin(userId, companyId)`

**Update Path:**
- Not observed.

**Deletion / Terminal Behavior:**
- Removing an admin removes their access to the company.

**Company Scoping:**
- Exists strictly to enforce company boundaries for users.

**Events:**
- None.

**Confidence:** High.

## Entity: Board Access Token
**Purpose:** Bearer token used by the UI ("board") to authenticate as a human operator for a specific company.

**Storage & Keys:**
- **Table:** `board_access_tokens` (`packages/db/src/schema/boardAccessTokens.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `token_hash` (text, NOT NULL, unique via index), `company_id`, `user_id`, `created_at`, `revoked_at`
- **FK:** `company_id` → `companies.id`

**Relationships:**
- Many-to-One: `companies` (via `company_id`)

**Creation Path:**
- Generated on login or board session creation.

**Update Path:**
- `revoked_at` set to invalidate.

**Deletion / Terminal Behavior:**
- Tokens are revoked (soft-deleted via `revoked_at`), not hard-deleted, for audit.

**Company Scoping:**
- Every token is scoped to exactly one `company_id`.

**Permissions:**
- Grants full board access (reads as full-control operator context per `AGENTS.md`).

**Events:**
- None observed.

**Confidence:** High.

## Entity: Project
**Purpose:** Container for issues (tickets). Provides grouping and optional `status` (e.g., active, paused, archived).

**Storage & Keys:**
- **Table:** `projects` (`packages/db/src/schema/projects.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `key` (text, unique within company), `name`, `description`, `status`, `company_id`, `created_at`, `updated_at`
- **Unique:** `projects_company_id_key_unique` on `(company_id, key)` (company-local uniqueness)

**Relationships:**
- Many-to-One: `companies` (via `company_id`)
- One-to-Many: `issues` (via `project_id`)

**Creation Path:**
- `POST /api/companies/:companyId/projects` → `projectService.create({ companyId, ... })`
- Verifies company access (`boardProjectQuery`), then inserts.

**Update Path:**
- `PATCH /api/companies/:companyId/projects/:projectId` → `projectService.update()`
- `DELETE /api/companies/:companyId/projects/:projectId` → `projectService.archive()` or `delete()` (observed as `.delete(deletedProject)`)

**Deletion / Terminal Behavior:**
- Projects may be archived or hard-deleted. Issues under a deleted project may be implicitly orphaned or cascade-deleted (not explicitly observed).

**Company Scoping:**
- `projectService.list(companyId)` enforces `where(eq(projects.companyId, companyId))`.

**Events:**
- None observed.

**Tests:**
- `createProject(companyId)` utility, tested in `companyRoutes.test.ts`.

**Confidence:** High.

## Entity: Agent API Key
**Purpose:** Secret key allowing an external AI agent to authenticate and act on behalf of the company.

**Storage & Keys:**
- **Table:** `agent_api_keys` (`packages/db/src/schema/agentApiKeys.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `name`, `key_hash` (text, NOT NULL), `scope` (text, default `'all'`), `company_id`, `last_used_at`, `revoked_at`, `created_at`, `updated_at`
- **Index:** `agent_api_keys_company_id` and `agent_api_keys_key_hash` (unique on `key_hash`)

**Relationships:**
- Many-to-One: `companies` (via `company_id`)

**Creation Path:**
- Board UI → `agentApiKeyService.create({ companyId, name, keyHash, scope })`

**Update Path:**
- `revoke()` sets `revoked_at` (soft delete)

**Deletion / Terminal Behavior:**
- Keys are revoked, not deleted, preserving audit trail.

**Company Scoping:**
- Every key is scoped to one `company_id`. Agents using a key cannot access other companies.

**Permissions:**
- Agents use these keys (bearer token) instead of board access tokens. Scope can be narrowed with `scope` field.

**Events:**
- None observed.

**Confidence:** High.

**Events:**

**Events:**

## Entity: Issue
**Purpose:** The primary human-to-agent work item (ticket). Captures a problem statement, desired outcome, and acceptance criteria. Issues are single-tracked and scoped to a project.

**Storage & Keys:**
- **Table:** `issues` (`packages/db/src/schema/issues.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `project_id`, `company_id`, `number`, `title`, `body`, `desired_outcome` (text), `acceptance_criteria` (text), `status` (text, default `'open'`), `priority` (text, default `'medium'`), `agent_label` (text), `assignee_type` (`'human' | 'agent'`), `assignee_id`, `parent_issue_id`, `created_by` (`'human' | 'agent'`), `created_by_id`, `human_status` (text), `agent_status` (text), `created_at`, `updated_at`
- **Unique:** `issues_project_id_number_unique` on `(project_id, number)` (local numbering)

**Relationships:**
- Many-to-One: `projects` (via `project_id`)
- Many-to-One: `companies` (via `company_id`)
- Self-Reference: `parent_issue_id` → `issues.id` (sub-issues)
- One-to-Many: `tasks` (via `issue_id`)
- One-to-Many: `comments` (on `issue_id`)

**Creation Path:**
- Human: `POST /api/companies/:companyId/projects/:projectId/issues` → `issueService.create(payload)` (returns `{ issueId }`)
- Number auto-incremented per project via sub-query (`(SELECT COALESCE(MAX(number), 0) + 1 FROM issues WHERE project_id = ...)`).

**Update Path:**
- `PATCH /api/companies/:companyId/issues/:issueId` → validates `companyId` ownership and updates fields.
- Status, assignee, and priority can be changed.

**Deletion / Terminal Behavior:**
- Status moves to `'closed'` or terminal value (see `03A_ISSUE_LIFECYCLE.md`).

**Company Scoping:**
- `issueService.listByProject(projectId, companyId)` enforces both `project_id` and implicitly `company_id` via project membership.

**Permissions:**
- Human operators can create, update, assign. Agents can read/create tasks linked to an issue but cannot directly mutate issue status without approval.

**Events:**
- `issue_status_changed`, `issue_assigned`.

**Confidence:** High.

## Entity: Task
**Purpose:** Represents an agent's commitment to work on an issue. The task is the single assignee (atomic checkout): one task per active issue, one agent per task. Tasks bridge an issue to a concrete execution unit (`run`).

**Storage & Keys:**
- **Table:** `tasks` (`packages/db/src/schema/tasks.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `issue_id`, `company_id`, `status` (text, default `'open'`), `created_at`, `updated_at`
- **Foreign Keys:** `issue_id` → `issues.id`, `company_id` → `companies.id`

**Relationships:**
- Many-to-One: `issues` (via `issue_id`)
- Many-to-One: `companies` (via `company_id`)
- One-to-Many: `runs` (via `task_id`)
- One-to-One-ish (per active): latest run is the active execution.

**Creation Path:**
- Agent checks out an open issue → `issueService.checkout()` → creates a `task` with `status = 'in_progress'` (or equivalent active state), atomically reserving the issue.

**Update Path:**
- Agent marks progress, blockers, completion via run events or explicit task update.
- Status transitions through `'open'`, `'in_progress'`, `'blocked'`, `'completed'`, `'cancelled'`, `'paused'`.

**Deletion / Terminal Behavior:**
- Terminal states: `'completed'`, `'cancelled'`. In terminal states, the single-assignee invariant is released, allowing a new task to be created for the same issue.

**Company Scoping:**
- `company_id` FK enforced in all lookups.

**Events:**
- `task_created`, `task_status_changed`.

**Tests:**
- `createTask(companyId, { issueId })` in test utilities; checked out via `issueService.checkout()` in `fetchAndAssignIssue`.

**Confidence:** High.

## Entity: Run
**Purpose:** A single session or execution attempt for a task. Captures the agent's actual work: steps, tool calls, and generated artifacts.

**Storage & Keys:**
- **Table:** `runs` (`packages/db/src/schema/runs.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `task_id`, `company_id`, `status` (text, default `'pending'`), `started_at`, `finished_at`, `created_at`, `updated_at`
- **FK:** `task_id` → `tasks.id`

**Relationships:**
- Many-to-One: `tasks` (via `task_id`)
- One-to-Many: `run_steps`
- One-to-Many: `run_transcript_entries`
- One-to-Many: `comments` (via `run_id`)

**Creation Path:**
- Starting a task spawns a run: `runService.start()`.

**Update Path:**
- Transitions through `'pending'`, `'running'`, `'paused'` (budget/approval gate), `'awaiting_approval'`, `'completed'`, `'failed'`.
- `runService.pauseRun()` — sets `status = 'paused'` and notifies the relevant task/issue via `runPauseNotified` event.

**Deletion / Terminal Behavior:**
- Terminal: `'completed'`, `'failed'`. A new run can be created for the same task if the task remains active.

**Company Scoping:**
- `company_id` enforced via joins or direct filter.

**Events:**
- `run_started`, `run_step_created`, `run_status_changed`, `run_pause_notified`.

**Tests:**
- `createRun(taskId)` utility.

**Confidence:** High.

## Entity: Run Step
**Purpose:** Granular record of actions within a run (e.g., planning, tool call, file edit, browser action, LLM API call).

**Storage & Keys:**
- **Table:** `run_steps` (`packages/db/src/schema/runSteps.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `run_id`, `type` (text, e.g., `'tool_use'`, `'thinking'`, `'llm_call'`), `status`, `input`, `output`, `thinking` (text), error info, `started_at`, `finished_at`, `created_at`, `updated_at`

**Relationships:**
- Many-to-One: `runs`

**Creation Path:**
- Agent adapter or orchestrator logs each action as a step: `runService.createStep()`.

**Update Path:**
- Status and output updated as the step progresses.

**Deletion / Terminal Behavior:**
- Steps are append-only (immutable).

**Company Scoping:**
- Implicit via `run_id` → `runs` → `tasks` → `issues` → `company_id`.

**Events:**
- Step creation triggers `run_step_created` events.

**Confidence:** High.

**Relationships:**
- Many-to-One: `runs`
- Many-to-One: `tasks` (via `task_id` for denormalized access)

**Deletion / Terminal Behavior:**
- Immutable.

**Company Scoping:**
- Denormalized `task_id` allows efficient company-scoped queries.

**Events:**
- None explicit; read by UI via polling or SSE.

**Confidence:** High.

## Entity: Comment
**Purpose:** Structured human-agent communication on an issue or run. Comments include mentions, status flags, and can carry decisions (approvals, denials, revisions, deferments).

**Storage & Keys:**
- **Table:** `comments` (`packages/db/src/schema/comments.ts`)
- **Primary Key:** `id` (UUID)
- **Fields:** `issue_id`, `run_id`, `company_id`, `created_by_type` (`'human' | 'agent'`), `created_by_id`, `content` (text), `json_content` (JSONB for structured mentions), `status`, `parent_comment_id`, `created_at`, `updated_at`

**Relationships:**
- Many-to-One: `issues` (optional, `issue_id`)
- Many-to-One: `runs` (optional, `run_id`)
- Self-Reference: `parent_comment_id` → `comments.id` (reply threading)
- Many-to-One: `companies`

**Creation Path:**
- Human posts via `POST /api/companies/:companyId/issues/:issueId/comments` → `commentService.create()`

**Update Path:**
- Edits tracked via `updated_at`, but for decision history, comments are append-only (new comments replace state, old ones persist).

**Deletion / Terminal Behavior:**
- Comments are immutable (soft semantics via `status` or `deleted_at` if added later).

**Company Scoping:**
- `company_id` on the comment row, plus validated via `issue_id` or `run_id` joins.

**Events:**
- `comment_created`.

**Tests:**
- `createComment(companyId, create)` utility.

**Confidence:** High.

## Architectural Contradictions
1. **Soft vs Hard Deletes:** Budget snapshots and audit logs must never be deleted (immutable), but projects can be hard-deleted (`projectService.delete(project)` — hard deletion, no `deleted_at` field observed). Comment system also lacks explicit `deleted_at` in schema, but the design expectation is immutability. Ensure `delete()` on projects and issues is reconciled with audit/compliance requirements.
2. **Denormalized `company_id` on child tables:** `run_transcript_entries` and `comments` both store `company_id` directly for query performance, but the canonical path is `run_id` → `task_id` → `issue_id` → `project_id` → `company_id`. Risk: if a row is moved across companies (not allowed), denormalized columns may drift. No enforcement trigger observed.
3. **Agent Label Taxonomy Ambiguity:** `issues.agent_label` is `text`, but it may be intended to map to specific adapter capabilities or agent types. No foreign key or enum enforces valid labels; a typo in the label may cause a task to be unrouteable.
4. **`issue_id` optional on comments:** Comments can optionally belong to an issue *or* a run. A comment orphaned from both lacks context linkage, yet the schema permits it. UI should guard against run-only comments that don't show up in issue threads.
5. **Issue Number vs UUID:** Issues have both `id` (UUID, internal) and `number` (integer, project-local). Public API references use `number` in some contexts and `id` in others. This dual-key surface increases API contract complexity.
